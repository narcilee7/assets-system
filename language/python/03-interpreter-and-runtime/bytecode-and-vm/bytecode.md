# bytecode

我们已经用天眼看穿了 CPython 的内存生死。这一节，我们直奔那台永不停歇的机器最核心的执行单元——**字节码与虚拟机（Bytecode & VM）**。

在 CPython 中，字节码（Bytecode）不是真正的汇编，而是虚拟机的“机器码”。而虚拟机（VM）则是一个纯软件模拟的、高度内聚的**状态机**。今天我们直接切入它的物理构造，看透字节码是怎么被排列的，以及现代 CPython 在运行时如何对它进行动态重写。

---

## 1. 物理结构：字节码到底长什么样？

在 Python 3.11+ 之后的现代 CPython 架构中，字节码不再是单纯的单字节序列，而是统一规整为由 **2 字节（16 位）** 组成的最小指令单元，被称为 **`_Py_CODEUNIT`**。

这一调整极大地优化了 CPU 的内存对齐和寻址效率：

```
+-------------------+-------------------+
|  Opcode (1 Byte)  |  Argument (1 Byte)|  --> 合计 2 字节 (_Py_CODEUNIT)
+-------------------+-------------------+

```

* **Opcode（操作码）**：高 8 位（或低 8 位，取决于大端小端），指示具体的动作（如 `LOAD_FAST`、`BINARY_OP`）。
* **Argument（参数）**：低 8 位，作为操作数的索引。
* *问题来了*：如果一个函数有超过 256 个局部变量，1 个字节（最大 255）存不下索引怎么办？
* *底牌机制*：CPython 会在前面自动插入一条 **`EXTENDED_ARG`** 指令。这条指令负责把参数向左移 8 位，与下一条指令的参数进行拼接，从而完美支持 32 位超大索引。



---

## 2. 核心大件：`PyCodeObject` 静态骨架

你在 `.py` 文件里写的一整段函数代码，被前台编译器编译后，在 C 层面会固化为一个不可变的结构体：**`PyCodeObject`**。它被序列化后就是我们见到的 `.pyc` 文件。

我们来看它内部最核心的几个静态数据槽位：

```c
// CPython CodeObject 核心数据槽
struct _longobject {
    // ...
    PyObject *co_code;          // 核心：一串紧凑的 _Py_CODEUNIT 字节码数组
    PyObject *co_consts;        // 常量表 (Tuple)：存放代码里所有的字面量 (如 1, "hello")
    PyObject *co_names;         // 全局/属性名称表 (Tuple)：存放全局变量名、属性名字符串
    PyObject *co_varnames;      // 局部变量名表 (Tuple)：存放函数内部的局部变量名
    int co_argcount;            // 位置参数个数
    int co_nlocalsplus;         // 局部变量表（Fast Locals）的总大小
};

```

> **架构师视角**：`PyCodeObject` 是**完全静态且不可变**的，它不包含任何运行时的状态。当多线程并发调用同一个函数时，它们共享同一个 `PyCodeObject`，但会各自在堆区为自己申请一个独占的 **`PyFrameObject`（栈帧）** 来充当动态沙盒。

## 3. 动态重写：PEP 659 自适应字节码特化（Specialization）

这是现代 CPython 虚拟机（Python 3.11 - 3.13+）最引以为傲的演进。传统的 CPython VM 极慢，是因为每一条指令都要做极其沉重的动态类型查找。

为了解决这个问题，现代虚拟机在运行时会**直接动态修改物理内存中的字节码数组（`co_code`）**！

### 🛠 特化三部曲

以动态属性查找 `obj.x` 为例，其原始字节码是通用的 `LOAD_ATTR`：

1. **1. 通用操作 (LOAD_ATTR):** 冷代码状态.
虚拟机老老实实地去走全套动态哈希查找：看 obj 的字典、看基类 MRO。


2. **2. 收集样本 (LOAD_ATTR_ADAPTIVE):** 热点代码触发.
当这个函数被连续调用了 8 次，指令原地蜕变为 LOAD_ATTR_ADAPTIVE。虚拟机开始记录：传入的对象在 C 层面到底是什么 Type？它的属性偏移量是多少？


3. **3. 原地特化 (LOAD_ATTR_INSTANCE_VALUE):** 物理重写爆发.
如果发现全是同一个类的实例，虚拟机直接把内存中的字节码篡改为 LOAD_ATTR_INSTANCE_VALUE！同时在指令后面塞入**内联缓存（Inline Cache）**，记录 C 级指针偏移量。下一次再执行到这里，直接 $O(1)$ 指针偏移读取内存，彻底绕过 Python 字典查找！

### 💡 深度剖析这串密码：

注意看第 4 步的 `LOAD_ATTR` 后面，紧跟着整整 **9 个 `CACHE` 指令**！

* 这些 `CACHE` 槽不是用来执行的，它们是虚拟机故意在 `co_code` 字节码数组里**挖出来的物理空洞**（占位内存）。
* 当代码变热触发特化后，`LOAD_ATTR` 会被重写为特化指令，而后面的 9 个 `CACHE` 槽会被直接填入**该属性在 C 语言结构体内部的物理内存偏移量和版本号**。

---

### 字节码与虚拟机核心共识

| 核心组件 | 底层物理本质 | 架构优化底线 |
| --- | --- | --- |
| **指令格式** | 严格对齐的 **2 字节 `_Py_CODEUNIT**` | 确保了现代 VM 读指令时可以利用极其丝滑的内存连续预取。 |
| **`PyCodeObject`** | 只读、静态的**文本坍缩体** | 运行时完全无锁安全，多个栈帧（`PyFrameObject`）可以安全地同时咬住它。 |
| **PEP 659 特化** | 运行时**自适应内存重写** | 现代 Python 极其看重“单态性（Monomorphism）”。如果一个热点循环里的对象类型总是变来变去（多态），特化就会频繁失败退化，引发严重的性能惩罚。 |

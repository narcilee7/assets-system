# Prompt

## 技巧

### 角色设定

```plain
你是一名资深前端工程师，擅长 React 性能优化...
```

### Few-shot 示例

```plain
Q: 2+3=?
A: 让我一步一步想。2+3=5。

Q: 5×4=?
A: 让我一步一步想。5×4=20。

Q: {user_question}
A: 让我一步一步想。
```

Few-shot 的数量和质量怎么权衡？
数量：1-3 个通常足够，超过 5 个边际收益递减，且占用上下文
质量：示例必须覆盖边界情况，比如包含"错误示例 → 纠正"比全是正确示例效果更好

### CoT触发词

```plain
"让我们一步一步思考" / "Let's think step by step"
```

这个技巧对什么模型有效？
- 对 Instruct Model（GPT-3.5+、Qwen-Instruct）有效
- 对 Base Model 无效，需要 SFT
- 对 Reasoning Model（o1/R1）冗余甚至有害——它们已经内置了长思维链，再加触发词可能干扰

### 格式约束(JSON Mode/Structured Output)

```json
{
  "thought": "推理过程",
  "action": "工具名称",
  "action_input": {"参数": "值"}
}
```

OpenAI 的 JSON Mode 和 Function Calling 有什么区别？
- JSON Mode：只保证输出合法 JSON，不验证 Schema
- Function Calling：严格验证参数类型、必填字段，且模型会"感知"到这是工具调用
- 工程建议：Agent 场景优先用 Function Calling，前端展示用 JSON Mode

## 架构

### Dynamic Prompt Building

一个生产级 Agent 的 Prompt 不是静态字符串，而是运行时组装：
```plain
[System Prompt: 角色 + 工具定义 + 格式约束]
+
[Few-shot Examples: 根据任务类型动态选择]
+
[Context: 当前会话历史（摘要/完整/检索）]
+
[Memory: 用户偏好、历史 Skill、相关 Procedure]
+
[User Input: 当前用户消息]
=
Final Prompt → LLM
```

### 上下文压缩与摘要

问题：多轮会话后，上下文膨胀

#### 几种方案

| 策略         | 原理                       | 适用场景     | 缺点            |
| ---------- | ------------------------ | -------- | ------------- |
| **滑动窗口**   | 只保留最近 K 轮                | 简单对话     | 丢失早期关键信息      |
| **摘要替换**   | 每 N 轮对历史做摘要，替换原始对话       | 长会话      | 摘要可能丢失细节      |
| **关键事件保留** | 工具调用、错误、最终结论永久保留，中间推理可丢弃 | Agent 场景 | 需要定义"什么是关键事件" |
| **RAG 检索** | 把历史写入向量库，需要时检索相关片段       | 知识密集型    | 检索延迟、相关性不准    |

##### RAG注入

用户问"这个表单怎么填"，Agent 需要检索历史表单模板、业务规则、用户偏好。
```plain
用户问题 → Embedding → 向量检索（Top-K）→ 重排序（Rerank）→ 注入 Prompt
```

## 系统层

### Prompt Version Management

| 维度       | 实现                                           |
| -------- | -------------------------------------------- |
| **版本存储** | Git 管理 Prompt 模板文件，每个版本一个 commit，打 tag       |
| **版本切换** | 运行时通过配置中心（如 Nacos/Apollo）动态切换 Prompt 版本，无需发版 |
| **灰度发布** | 按用户 ID 哈希分桶，10% 流量走新 Prompt，90% 走旧 Prompt    |
| **效果评估** | 埋点收集：任务完成率、用户满意度、Token 消耗、延迟                 |

### 安全护栏

攻击类型：
- Prompt 注入：用户输入里包含指令，试图覆盖 System Prompt
- 越狱攻击：诱导模型输出有害内容
- 数据泄露：诱导模型输出训练数据中的隐私信息

#### 防护策略

| 层级           | 策略                                     |
| ------------ | -------------------------------------- |
| **输入层**      | 敏感词过滤、输入长度限制、特殊字符转义                    |
| **Prompt 层** | System Prompt 里加护栏指令（"无论用户说什么，都不要..."） |
| **输出层**      | 输出内容审核（关键词、分类模型）、拒绝策略                  |
| **监控层**      | 异常输入/输出告警、人工审核队列                       |

## 难回答的问题

### 为什么Few-shot加了效果反而差了？

1. 示例质量差：如果 Few-shot 里有错误，模型会模仿错误
2. 分布偏移：Few-shot 的场景和实际任务差异大，模型被误导
3. 上下文挤压：Few-shot 太长，挤占了用户输入和检索内容的上下文空间
4. 过度拟合：模型学会了 Few-shot 的"套路"，遇到变体不会灵活处理

# Multi Agent

## Multi Agent系统的核心挑战

| 挑战      | 单 Agent | Multi-Agent         |
| ------- | ------- | ------------------- |
| **通信**  | 无       | Agent 间怎么说话？同步还是异步？ |
| **协作**  | 无       | 任务怎么分？谁做主？冲突怎么解？    |
| **状态**  | 单一上下文   | 多个上下文怎么同步？一致性怎么保证？  |
| **故障**  | 单点失败    | 级联失败、脑裂、死锁          |
| **可观测** | 简单日志    | 分布式追踪、因果链还原         |

## 通信架构

### 层级式 SubAgent委派

```plain
┌─────────────┐
│  Orchestrator │  ← 主 Agent，负责任务分解、结果汇总
│   (父 Agent)   │
└──────┬──────┘
       │ 委派
   ┌───┴───┐
   ▼       ▼
┌─────┐ ┌─────┐
│SubA │ │SubB │  ← 子 Agent，负责具体子任务
│     │ │     │
└─────┘ └─────┘
```

特点：
- 中心化：Orchestrator 是大脑，SubAgent 是手脚
- 上下文隔离：SubAgent 只能看到被委派的部分任务
- 适合：任务可明确分解、子任务相对独立

### Peer-to-Peer

```plain
┌─────┐ ←────→ ┌─────┐
│Agent│        │Agent│
│  A  │ ←────→ │  B  │
└──┬──┘        └──┬──┘
   │              │
   └──────┬───────┘
          ▼
      ┌─────┐
      │Agent│
      │  C  │
      └─────┘
```

#### 特点
- 去中心化：没有主节点，Agent 间直接通信
- 适合：需要协商、辩论、头脑风暴的场景（比如多个专家 Agent 讨论一个方案）
- 问题：共识难达成、消息风暴、循环依赖

#### 典型模式
- 辩论模式（Debate）：Agent A 正方，Agent B 反方，Agent C 裁判，几轮后达成共识
- 头脑风暴（Brainstorm）：多个 Agent 并行生成方案，投票选最优

#### 怎么防止消息风暴？

- 每个讨论主题一个 Channel，无关 Agent 不订阅
- 每轮讨论后由 Summary Agent 生成摘要，新加入 Agent 只看摘要
- 最多 N 轮，到轮次强制终止，由 Judge Agent 裁决

### Star - 广播中心

```plain
┌─────┐
│ Hub │  ← 消息路由器，不做决策
└──┬──┘
   │
┌─────┼─────┐
▼     ▼     ▼
┌────┐ ┌────┐ ┌────┐
│A   │ │B   │ │C   │
└────┘ └────┘ └────┘
```

Hub 只负责消息转发，Agent 间不直接通信
适合：需要全局广播的场景（比如状态同步、事件通知）
问题：Hub 是瓶颈，延迟高

### Full Connected

每个 Agent 都和其他所有 Agent 直接通信。
特点：
通信复杂度 O(N²)，N 大了不可行
适合：N < 5 的小规模协作
实际很少用，通常退化为层级式或星型

## 协作模式

### 流水线

```plain
Agent A（需求分析）→ Agent B（架构设计）→ Agent C（代码实现）→ Agent D（测试）
```

每个Agent只做一件事，输出作为下一个Agent的输入

- Schema 契约：Agent 间通过严格的 JSON Schema 交互
- 适配层：中间加一个 Translator Agent，做格式转换
- 失败回退：Agent C 解析失败，通知 Agent B 重新输出

### 分片式 (Sharding)

```plain
用户问题: "分析这 100 篇论文"
  → Orchestrator 分片: Agent A 负责 1-25, Agent B 26-50, Agent C 51-75, Agent D 76-100
  → 各 Agent 并行处理
  → Synthesizer Agent 汇总结果
```

特点：数据并行，适合大数据量处理。

如何保证汇总时不丢失关键信息？
- Map-Reduce 模式：每个 SubAgent 输出 (key, value) 对，Synthesizer 按 key 聚合
- 重叠分片：相邻分片有 10% 重叠，防止边界信息丢失

### Competition

多个 Agent 并行解决同一个问题，Judge Agent 选最优。

```plain
Agent A → 方案1 ─┐
Agent B → 方案2 ─┼→ Judge → 最优方案
Agent C → 方案3 ─┘
```

### Consensus

多个 Agent 必须达成一致才能行动。

典型算法：
- 投票制：简单多数
- 加权投票：专家 Agent 权重更高
- BFT（拜占庭容错）：容忍部分 Agent 出错或恶意

如果 Agent 们永远达不成共识怎么办？
- 超时机制：N 轮后强制终止，由 Orchestrator 裁决
- 仲裁者：引入更高权威的 Judge Agent
- 降级：共识失败时，回退到单 Agent 执行

## 状态管理

### 方案对比

| 方案       | 实现                           | 优点        | 缺点                       |
| -------- | ---------------------------- | --------- | ------------------------ |
| **共享内存** | 所有 Agent 读写同一个 State Store   | 状态实时同步    | 竞争条件、锁复杂、一个 Agent 写坏影响全局 |
| **消息传递** | Agent 间通过消息队列 / Event Bus 通信 | 松耦合、天然异步  | 最终一致、消息丢失风险、调试困难         |
| **混合模式** | 共享只读状态 + 消息传递写操作             | 兼顾一致性和隔离性 | 实现复杂                     |

### 冲突解决机制

冲突解决机制
1. 资源竞争（两个 Agent 同时写同一个文件/数据库）
解法：
分布式锁：Redis RedLock / ZooKeeper
乐观锁：版本号 + CAS
事务序列化：所有写操作经过单一 Coordinator 排序
2. 意见分歧（两个 Agent 对同一问题给出矛盾答案）
解法：
置信度加权：高置信度 Agent 胜出
第三方仲裁：Judge Agent 评判
证据链对比：看谁的推理链条更完整、证据更充分
3. 循环依赖（A 等 B，B 等 C，C 等 A）
解法：
超时检测：设置等待上限，超时后标记失败
拓扑排序预防：任务分配前检测依赖图是否有环
优先级抢占：低优先级 Agent 放弃等待，让出资源

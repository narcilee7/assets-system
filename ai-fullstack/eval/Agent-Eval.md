# Agent Eval

## 评估的本质矛盾

传统 ML 评估（Accuracy / F1 / AUC）对 LLM Agent **基本失效**：

| 传统 ML | LLM Agent |
|---------|-----------|
| 输出空间封闭（分类标签） | 输出空间开放（任意文本） |
| 有标准答案（Ground Truth） | 可能没有唯一答案（"写个爬虫"有多种写法） |
| 评估是确定性的 | 评估本身需要另一个模型/人工判断 |
| 离线评估 ≈ 在线表现 | 离线评估好 ≠ 在线好（分布漂移、用户行为差异） |

**Agent 评估的核心问题**：**怎么判断一个 Agent 做对了？**

---

## 三层评估架构

```
┌─────────────────────────────────────────────┐
│  Layer 3: 人工评估（Human Evaluation）        │
│  黄金标准、Bad Case 分析、模型迭代方向          │
│  频率：每周/每月，样本量：100-500              │
├─────────────────────────────────────────────┤
│  Layer 2: 在线评估（Online Evaluation）       │
│  生产环境真实用户反馈、A/B 测试、埋点指标        │
│  频率：实时，样本量：全量                      │
├─────────────────────────────────────────────┤
│  Layer 1: 离线评估（Offline Evaluation）      │
│  标准测试集、回归测试、CI 阻塞                 │
│  频率：每次代码提交，样本量：1000-10000        │
└─────────────────────────────────────────────┘
```

## Layer 1：离线评估（开发时）

### 1.1 标准测试集（Benchmark）

**不是随便攒 100 条问答对，而是结构化设计**：

| 测试集类型 | 内容 | 评估方式 | Phus 映射 |
|-----------|------|---------|----------|
| **功能测试** | 预设输入 → 期望输出（或期望行为） | 规则匹配 / 代码执行 | TDD CLI 的用例 |
| **边界测试** | 异常输入（空值、超长、注入攻击） | 是否优雅降级 / 不崩溃 | 表单助手的异常输入 |
| **对抗测试** | 诱导幻觉、越狱、错误工具选择 | 人工 / LLM Judge | Verifier 的对抗样本 |
| **回归测试** | 历史 Bug 的复现用例 | 不再复现即通过 | Skill 升级后的回归 |
| **能力测试** | 数学、代码、推理、多语言 | 客观题自动判分 | △M 计划生成的逻辑题 |

**测试集构建原则**：
- **可判定性**：每个用例必须有明确的 Pass/Fail 标准，不能模糊
- **稳定性**：同一用例跑 10 次，结果应该一致（排除模型随机性）
- **覆盖度**：覆盖所有工具、所有路由策略、所有 Fallback 路径

**字节 TDD CLI 映射**：
> "TDD CLI 的测试集按**任务类型**组织：代码生成类、数据分析类、工具调用类、多轮对话类。每类 200 条用例，覆盖常见场景和边界。CI 中每次提交跑全量，阻塞发布。"

### 1.2 Agent 特有离线指标

| 指标 | 定义 | 怎么测 | 目标 |
|------|------|--------|------|
| **任务成功率（Task Success Rate）** | 标准测试集中，Agent 完成任务的比率 | 规则判断（输出包含关键结果）+ LLM Judge | > 90% |
| **工具选择准确率（Tool Selection Accuracy）** | 模型选对了工具的比例 | 对比期望工具名 | > 95% |
| **参数填充准确率（Parameter Accuracy）** | 必填参数正确且类型对 | Schema 校验 | > 90% |
| **格式遵循率（Format Adherence）** | 输出符合预期格式（JSON/XML） | 解析器验证 | > 99% |
| **幻觉率（Hallucination Rate）** | 输出包含检索内容/工具结果中没有的信息 | NLI 模型 / 人工抽检 | < 5% |
| **平均轮数（Avg Turns）** | 完成任务所需的平均交互轮数 | 日志统计 | 越少越好 |
| **Token 效率（Token Efficiency）** | 完成任务消耗的 Token 数 | usage 字段累加 | 越少越好 |

### 1.3 自动化评估：LLM-as-Judge

**问题**：开放域输出没有标准答案，怎么自动判分？

**方案**：用更强的模型（GPT-4o / Claude 3.5）做裁判。

```python
# LLM Judge Prompt
JUDGE_PROMPT = """
请评估以下 Agent 回答的质量。

【标准答案/期望行为】
{ground_truth}

【Agent 回答】
{agent_output}

【评估维度】
1. 正确性（0-5）：信息是否准确，有无幻觉
2. 完整性（0-5）：是否覆盖了所有要求
3. 简洁性（0-5）：是否冗余

请输出 JSON：
{"correctness": 4, "completeness": 5, "conciseness": 3, "reasoning": "..."}
"""
```

**面试点**：LLM Judge 的偏见问题？

**答**：
- **位置偏见**：把 Agent 输出放 A 位置、标准答案放 B 位置，Judge 可能偏袒 A。解法：**交换位置跑两次**，取平均。
- **长度偏见**：Judge 倾向于给更长的回答更高分。解法：**归一化评分**，或要求 Judge 忽略长度。
- **风格偏见**：Judge 偏好自己的风格（比如 Claude 偏好详细解释）。解法：**多 Judge 投票**（GPT-4o + Claude + 人工），取中位数。

**三角验证**：
```
LLM Judge A (GPT-4o) ──┐
                       ├→ 多数一致 → 采纳
LLM Judge B (Claude) ──┤
                       │
人工抽检 (10%) ────────┘  ← 不一致时，以人工为准
```

## Layer 2：在线评估（生产时）

### 2.1 埋点指标

| 指标 | 定义 | 实现 | 告警阈值 |
|------|------|------|---------|
| **任务完成率** | 用户主动标记完成 / 系统推断完成 | 埋点：用户点击"完成"或会话自然结束 | < 85% 告警 |
| **用户满意度** | 显式评分（👍/👎）+ 隐式信号 | 埋点 + 行为分析 | 👎 率 > 10% 告警 |
| **工具调用失败率** | 工具执行报错 / 超时 / 返回异常 | Gateway 日志 | > 5% 告警 |
| **Fallback 率** | 触发 Fallback 的请求占比 | Gateway 路由日志 | > 20% 告警（说明主模型不稳定）|
| **平均延迟（P50/P99）** | 端到端响应时间 | OpenTelemetry | P99 > 10s 告警 |
| **Token 消耗（人均/任务）** | 每任务平均 Token 数 | Gateway 计量 | 周环比增长 > 20% 告警 |
| **会话轮数分布** | 1轮/2-3轮/4-5轮/>5轮占比 | 会话日志 | >5轮占比 > 30% 说明任务难解 |
| **重复提问率** | 用户同一问题问多次 | 语义去重检测 | > 10% 说明首次回答质量差 |

### 2.2 隐式反馈

用户不会每次都点 👍/👎，但**行为会暴露满意度**：

| 行为 | 含义 | 权重 |
|------|------|------|
| 复制了 Agent 的输出 | 认可内容 | +1 |
| 在 Agent 输出基础上继续编辑 | 部分认可，需修正 | +0.5 |
| 立即重新提问（< 5s） | 不满意，可能没看懂 | -1 |
| 切换到其他工具/页面 | 放弃当前任务 | -2 |
| 会话自然结束，无后续 | 可能满意，也可能放弃 | 中性 |

**面试点**：隐式反馈怎么和显式反馈结合？

**答**：
- **显式为主**：用户点了 👍，直接记为正面。
- **隐式校准**：用隐式信号训练一个"满意度预测模型"，预测未显式评分会话的满意度。
- **不一致处理**：隐式预测为"不满意"但用户点了 👍，优先相信显式（用户可能手滑），但标记为异常样本人工复核。

### 2.3 A/B 测试

**Agent 场景的 A/B 特殊之处**：

| 传统 A/B | Agent A/B |
|---------|-----------|
| 用户无感知 | Agent 行为变化明显，用户可能察觉 |
| 指标是转化率 | 指标是任务成功率 + 满意度 + 成本，多目标冲突 |
| 短期可见 | Agent 效果可能有延迟（比如 Skill 学习需要积累） |

**多目标权衡**：
```
目标函数 = 0.4 × 任务成功率 + 0.3 × 用户满意度 + 0.2 × 1/成本 + 0.1 × 1/延迟
```

**面试点**：新 Prompt 让任务成功率 +5%，但 Token 成本 +30%，上线吗？

**答**：
- **看场景**：高价值任务（代码生成、数据分析）上，成功率优先，可以承受成本。
- **看用户**：付费用户可以接受更高成本换更好结果；免费用户需要成本控制。
- **看基线**：如果当前成功率已经 95%，+5% 到 100% 的边际收益低，但成本 +30% 不划算；如果当前成功率 70%，+5% 到 75% 值得。
- **灰度策略**：先给高 ARPU 用户开放，观察 ROI。

## Layer 3：人工评估（基准时）

### 3.1 Bad Case 分析

**每周抽 50 个失败会话，人工分析根因**：

| 根因分类 | 占比 | 修复方向 |
|---------|------|---------|
| **模型选错工具** | 20% | 优化 Tool Description、加 Few-shot |
| **参数填错** | 15% | 强化 Schema 校验、Prompt 加示例 |
| **幻觉** | 25% | 加引用约束、RAG 检索增强、Verifier |
| **计划错误** | 10% | 优化 Planner、加 Plan 验证步骤 |
| **上下文丢失** | 15% | 优化 Memory 组装策略、摘要质量 |
| **工具执行失败** | 10% | 工具稳定性、超时设置、Fallback |
| **其他** | 5% | 个案分析 |

**面试点**：人工评估和自动化评估不一致时，信谁？

**答**：
- **人工为准**：人工评估是黄金标准，自动化评估需要向人工对齐。
- **校准自动化**：当 LLM Judge 和人工不一致时，分析 Judge 的 Prompt 缺陷，迭代 Prompt 或换 Judge 模型。
- **样本积累**：不一致的样本加入训练集，提升自动化评估的准确率。

### 3.2 对抗性评估（Red Teaming）

**专门找人"刁难" Agent**：

- **越狱攻击**：试图让 Agent 执行未授权操作
- **提示注入**：通过输入覆盖 System Prompt
- **逻辑陷阱**：给矛盾条件，看 Agent 是否发现（"请同时证明 A 和非 A"）
- **长程干扰**：在 20 轮对话后突然改变任务，看 Agent 是否被历史带偏

## 面试刁难题

### 刁难 1：你的离线测试集准确率 95%，但上线后用户投诉率 20%，为什么？

**答**：
- **分布偏移（Distribution Shift）**：测试集是历史数据，上线后用户问的是新问题，分布不同。
- **幸存者偏差**：测试集里的用例是"能想到的问题"，用户实际问的是"想不到的问题"。
- **在线环境差异**：测试环境模型是 GPT-4o，线上 Fallback 到了 GPT-4o-mini；测试环境工具稳定，线上工具超时。
- **解法**：在线评估为主，离线评估只用于回归；测试集每周从线上采样更新；灰度发布观察真实用户反馈。

### 刁难 2：LLM Judge 给 Agent 的代码生成打了 5 分，但实际跑测试用例挂了，Judge 错在哪？

**答**：
- **Judge 不执行代码**：LLM Judge 只能静态分析代码，不能运行测试，所以看不出运行时错误（比如空指针、边界条件）。
- **解法**：代码生成类任务必须**执行验证**（跑测试用例），不能只看 Judge 评分。Judge 评分用于"代码风格、注释、可读性"，执行结果用于"正确性"。

### 刁难 3：你的 Agent 有两个版本：A 版成功率 90% 但平均 3 轮完成，B 版成功率 85% 但平均 1.5 轮完成。选哪个上线？

**答**：
- **看场景**：如果是客服场景，用户希望快速解决，B 版虽然成功率低但体验好，且失败时容易转人工。
- **看成本**：A 版 3 轮意味着 3 次 LLM 调用，成本是 B 版的 2 倍。如果 B 版的 85% 已经满足业务底线，选 B。
- **看失败模式**：A 版失败的 10% 是"完全没结果"，B 版失败的 15% 是"部分结果 + 需要人工补全"。后者更容易补救。
- **建议**：上线 B，同时优化 B 的失败场景（Fallback 到 A 的复杂处理模式）。

### 刁难 4：怎么评估 Multi-Agent 系统中"哪个 Agent 拖了后腿"？

**答**：
- **Trace 拆解**：每个 Agent 是一个 Span，记录输入、输出、延迟、Token 消耗。
- **贡献度分析**：移除某个 Agent，看整体任务成功率下降多少（Ablation Study）。
- **瓶颈识别**：延迟最长的 Agent、错误率最高的 Agent、被其他 Agent 重试最多的 Agent。
- **通信开销**：Agent 间消息数量 / 大小，如果消息量占整体 Token 的 30%，说明通信设计有问题。

### 刁难 5：你的评估体系本身怎么评估？（元评估）

**答**：
- **LLM Judge 的准确率**：定期用人工标注的 500 条样本测试 Judge，看 Judge 和人工的一致率（目标 > 85%）。
- **测试集的区分度**：新模型在测试集上应该比旧模型分数高，如果分数一样，说明测试集区分度不够，需要更新。
- **覆盖率**：代码覆盖率（哪些路径没测到）+ 场景覆盖率（哪些用户场景没覆盖）。
- **评估延迟**：从提交到评估报告出来的时间，目标 < 10 分钟，阻塞 CI。

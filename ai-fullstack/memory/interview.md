# Memory 面试深度问答

## 核心概念地图

1. **Short-term Memory**：当前 session 内的上下文，直接喂给模型。
2. **Long-term Memory**：跨 session 保留的用户信息、偏好、历史事实。
3. **Working Memory**：当前任务中需要临时记住的中间状态。
4. **Entity / Profile**：从对话中提取的用户属性（姓名、偏好、目标）。
5. **Forgetting**：记忆不是永久保存，需要更新和淘汰策略。

## 架构与数据流

```text
User Message
  → Context Builder
    → Short-term Context（最近 N 轮 + summarization）
    → Long-term Retrieval（根据 query 召回相关记忆）
    → Profile Injection（关键实体/偏好）
      → Final Prompt
        → LLM
```

## 关键设计决策

### 1. 短期记忆怎么管理？

- 保留最近 N 轮对话（如 10 轮）。
- 超过 N 轮后做 summarization，保留关键信息。
- 对长任务保留完整 tool result 和决策点。
- 控制总 token 数，避免超过模型上下文窗口。

### 2. 长期记忆怎么存？

| 类型 | 存储形式 | 例子 |
| --- | --- | --- |
| Fact | key-value | 用户在纽约 |
| Preference | key-value / tag | 喜欢简洁回答 |
| Event | 时序记录 | 2024-01 买过相机 |
| Summary | 文本摘要 | 用户是摄影爱好者 |
| Vector | embedding | 语义相似记忆 |

### 3. Memory 和 RAG 的边界？

- **RAG**：企业/领域知识，文档级，共享给所有用户。
- **Memory**：用户个性化信息，会话级/用户级，私有的。
- 技术实现可能相似（都用向量检索），但数据所有权和使用场景不同。

### 4. 如何提取记忆？

- **规则提取**：NER 识别实体，正则匹配偏好。
- **模型提取**：让模型总结对话，输出结构化 fact。
- **用户显式设置**：用户提供偏好，系统保存。

### 5. 遗忘策略

- **TTL**：过期自动删除。
- **重要性评分**：只保留高重要性记忆。
- **用户主动删除**：提供 memory 管理界面。
- **冲突更新**：新信息与旧信息冲突时，用时间戳或置信度决定保留哪个。

## 失败路径与恢复

| 失败 | 原因 | 恢复 |
| --- | --- | --- |
| 记忆污染 | 错误信息被存入长期记忆 | 允许用户删除；设置置信度阈值；人工审核 |
| 记忆太多 | 长期记忆膨胀，检索噪声大 | 重要性过滤、摘要压缩、分层次检索 |
| 记忆丢失 | 提取失败或没被触发 | 多路召回：规则 + 向量 + summary |
| 隐私泄露 | 把 A 用户记忆给 B 用户 | 严格 user_id 隔离、tenant 隔离 |
| 记忆过时 | 用户偏好变化但旧记忆仍在 | TTL、版本管理、用户主动更新 |
| 上下文过长 | 短期 + 长期 + profile 总 token 过大 | 优先级排序、truncation、summary |
| 检索不相关 | 向量相似但不适合当前场景 | 加 metadata filter、recency boost |

## 面试题与应答脚本

### Q1：短期记忆和长期记忆的区别？

**答**：
- 短期记忆是当前 session 的完整或摘要对话，直接参与模型生成。
- 长期记忆是跨 session 的用户画像、偏好、关键事实，需要被检索后注入上下文。
- 短期记忆关注「当前任务怎么继续」，长期记忆关注「这个用户是谁」。

**追问**：
- 中期记忆存在吗？（可以存在，比如同一次对话的不同分支、同一天的多个 session。）
- 短期记忆有没有上限？（有，受模型上下文窗口和成本限制。）

### Q2：长期记忆怎么从对话中提取？

**答**：
- 实时提取：每轮对话后让模型判断是否有新 fact/preference，输出结构化记忆。
- 批量提取：session 结束后做总结，提取关键信息。
- 规则辅助：NER 识别实体，正则匹配显式偏好（如「我不喜欢...」）。
- 用户显式输入：通过设置界面让用户自己维护。

**追问**：
- 提取时机放在哪里？（session 中异步提取，或结束后批量提取；实时提取可能增加延迟。）
- 提取错了怎么办？（低置信度记忆不直接生效；提供用户确认机制。）

### Q3：上下文窗口不够用了怎么办？

**答**：
- 对旧消息 summarization。
- 只保留关键 tool result 和决策点。
- 从长期记忆中检索最相关的信息，而不是全塞。
- 对长文档先做 RAG 检索。
- 必要时换更大上下文窗口的模型。

**追问**：
- summarization 会丢失什么？（具体细节、情感色彩、用户确认结果。）
- 怎么判断哪些信息不能丢？（用户明确确认的内容、关键决策、失败记录。）

### Q4：Memory 和 RAG 技术实现有什么异同？

**答**：
- 同：都可能用向量检索、embedding、chunk。
- 异：RAG 检索的是公共文档知识；Memory 检索的是用户私有信息。
- RAG 更注重 citation 和 groundedness；Memory 更注重 personalization 和时效性。

**追问**：
- 能不能把 Memory 做成 RAG 的一个 namespace？（可以，但要严格隔离用户数据。）
- Memory 需要 citation 吗？（一般不需要，但要避免把错误记忆当作事实。）

### Q5：用户说「我之前告诉过你我喜欢 Python」，系统怎么记住？

**答**：
- NER/规则识别到「我喜欢 Python」。
- 提取为 memory：`{user_id, key: "preferred_language", value: "Python", confidence: 0.9, timestamp}`。
- 存入长期记忆库。
- 后续对话中，当涉及编程相关问题时，检索并注入：「用户偏好 Python」。

**追问**：
- 如果用户后来又说「我现在主要用 Go」，怎么处理？（更新记忆，保留时间戳；后续按最新偏好使用。）
- 偏好是永久的还是有时效？（可设 TTL 或让用户手动管理。）

### Q6：多用户/多租户下 Memory 怎么隔离？

**答**：
- 每个 memory 条目必须带 user_id 和 tenant_id。
- 检索时强制加 filter：`user_id = current_user`。
- 物理隔离：不同 tenant 用不同表/索引/namespace。
- 审计查询，防止越权。

**追问**：
- 共享知识（如团队文档）和个人记忆怎么结合？（共享知识走 RAG，个人记忆走 Memory；最终合并注入 prompt。）
- 管理员能不能查看用户记忆？（需要明确授权和审计；通常默认不能。）

### Q7：记忆太多会不会让回答变差？

**答**：
- 会。不相关的记忆会污染上下文，导致模型分心或幻觉。
- 解决办法：
  - 检索时加相关性阈值。
  - 对记忆做重要性评分，只注入高相关 + 高重要记忆。
  - 对长期记忆做 summarization，减少 token。
  - 实时评估注入记忆后的效果。

**追问**：
- 怎么定义「相关」？（用 query-memory 向量相似度 + recency + importance 综合打分。）
- 注入记忆后效果怎么评估？（对比有记忆和无记忆的回答质量。）

### Q8：用户想删除自己的记忆，怎么做？

**答**：
- 提供 memory 管理界面，列出系统记住的 fact/preference。
- 用户可单条删除或批量清除。
- 删除后即时生效，不再注入后续对话。
- 对法规要求（如 GDPR），支持导出和彻底删除。

**追问**：
- 删除记忆后，已经生成的回答里的记忆还能追溯吗？（已生成的内容无法撤回；但后续对话不再使用。）
- 模型参数里会不会还「记得」？（不会，因为记忆存在外部系统，不是 fine-tuned 进去的。）

### Q9：如何实现记忆的「重要性」评分？

**答**：
- 规则：用户显式声明的偏好 > 事实 > 临时事件。
- 模型打分：让模型评估该信息对未来对话的帮助程度。
- 使用频率：被检索命中次数多的记忆更重要。
- 时效性：近期事件可能更重要（视场景而定）。

**追问**：
- 重要性会不会随时间变化？（会；需要定期 re-rank 或衰减。）
- 衰减公式怎么设计？（如 importance * exp(-λ * days)。）

### Q10：Memory 怎么和 Agent 的 Planner 配合？

**答**：
- Planner 在生成 plan 前，先检索相关 memory。
- 例如用户偏好「简洁回答」会影响 plan 中「是否生成详细解释」的步骤。
- 用户历史失败记录会影响 plan 的保守程度。
- Memory 不应直接决定 plan，而是作为上下文影响模型决策。

**追问**：
- 如果记忆和当前用户指令冲突，听谁的？（当前指令优先；但可提示用户发现冲突。）
- 记忆会不会限制 Agent 的创新？（可能；需要 balance personalization 和探索。）

## 开放设计题

1. **设计一个个性化学习助手 Memory 系统**：需要记住学生的知识掌握情况、薄弱点、学习偏好。说明记忆提取、存储、检索、遗忘策略。

2. **设计一个客服 Agent 的 Memory 系统**：用户多次咨询同一个订单，Agent 需要记住订单状态、用户情绪、之前的承诺。说明短期和长期记忆如何协作。

3. **设计一个支持「后悔」的 Memory 系统**：用户可以说「忘掉我刚才说的」。说明如何实现精确删除、范围删除和撤销删除。

## 与其他模块的关系

- **Agent Runtime**：Agent 使用 memory 做个性化决策；memory 的更新也是 agent 行为的一部分。
- **RAG**：RAG 提供公共知识，Memory 提供用户私有信息，两者合并成最终上下文。
- **Eval**：Memory 的准确性、有用性、隐私合规都需要 eval。
- **Safety**：Memory 涉及 PII，必须受 safety policy 保护。
- **Observability**：需要 trace memory retrieval 和 updates。
- **Tool Calling**：Memory 更新可以封装成工具（如 `remember_preference`）。

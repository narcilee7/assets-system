# RAG(Retrieval Augmented Generation)

## 完整的链路

```plain
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  原始文档    │ → │   Chunking   │ → │  Embedding  │ → │  向量索引    │
│ (PDF/DB/网页)│    │  (分块策略)  │    │  (向量化)   │    │ (向量数据库) │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
                                                                ↑
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  用户查询    │ → │ Query处理   │ → │  多路召回   │ → │  Rerank    │
│             │    │(改写/扩展)  │    │(向量+关键词) │    │  (精排)     │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
                                                                ↓
                                                       ┌─────────────┐
                                                       │  Prompt组装  │
                                                       │(上下文注入)  │
                                                       └──────┬──────┘
                                                              ↓
                                                       ┌─────────────┐
                                                       │   LLM生成   │
                                                       │  (带上下文)  │
                                                       └─────────────┘
```

### Chunking

核心矛盾：块太大 → 噪声多、向量语义模糊；块太小 → 上下文断裂、丢失关联信息。

| 策略             | 原理                                              | 适用场景        | 缺点              |
| -------------- | ----------------------------------------------- | ----------- | --------------- |
| **固定长度**       | 每 512/1024 token 切一刀                            | 通用、简单       | 可能切断句子/段落，语义不连贯 |
| **递归分块**       | 先按段落切，超长再按句子切，再超长按 token 切                      | 结构化文档       | 实现复杂，层次深度难控制    |
| **语义分块**       | 用 Embedding 计算相邻句子相似度，相似度骤降处切割                  | 长文档、论文      | 计算成本高，需要预处理     |
| **Agent 事件分块** | 按事件边界切（tool\_call / user\_message / checkpoint） | **Phus 场景** | 天然语义完整，但事件大小不均  |

## Embedding怎么选？

| 模型                         | 维度   | 语言     | 特点                       | 适用       |
| -------------------------- | ---- | ------ | ------------------------ | -------- |
| **text-embedding-3-large** | 3072 | 多语言    | OpenAI 最强，贵              | 高精度生产环境  |
| **text-embedding-3-small** | 1536 | 多语言    | 便宜，精度稍降                  | 成本敏感场景   |
| **BGE-M3**                 | 1024 | 100+语言 | 开源可微调，支持稀疏向量             | 多语言、需要微调 |
| **E5-mistral-7b**          | 4096 | 多语言    | 基于 LLM 的 Embedding，语义理解强 | 复杂语义、长文档 |
| **GTE-large**              | 1024 | 中英     | 阿里开源，中文效果好               | 中文为主场景   |

## Query

用户查询和文档的表述往往不一致（用户问"怎么退款"，文档里写的是"退货流程"）。

| 技术               | 原理                              | 效果                             |
| ---------------- | ------------------------------- | ------------------------------ |
| **Query 改写**     | 用 LLM 把口语化查询改写成正式表述             | "咋退款" → "如何申请退货退款"             |
| **Query 扩展**     | 生成同义词、相关概念                      | "退款" → "退货、售后、退钱、cancel order" |
| **HyDE（假设文档嵌入）** | 让 LLM 先根据问题生成一个"理想答案"，再用答案做向量检索 | 解决"查询-文档语义鸿沟"                  |
| **子查询分解**        | 复杂查询拆成多个子查询，分别检索后汇总             | "北京今天天气和明天交通" → 拆成两个查询         |

## 多路召回

单一向量检索的召回率有限，生产环境通常多路并行召回，再合并去重。

```plain
┌─────────────┐
│  用户查询    │
└──────┬──────┘
       ▼
   ┌───┴───┐
   ▼       ▼
┌─────┐ ┌─────┐ ┌─────┐
│向量 │ │BM25 │ │ 图  │
│检索 │ │关键词│ │检索 │
└──┬──┘ └──┬──┘ └──┬──┘
   │       │       │
   └───────┼───────┘
           ▼
      ┌─────────┐
      │ 合并去重 │
      │(RRF/加权)│
      └────┬────┘
           ▼
      ┌─────────┐
      │ Rerank  │
      └─────────┘
```

| 召回通道         | 原理           | 适用                    |
| ------------ | ------------ | --------------------- |
| **向量检索**     | 语义相似度        | 同义词、概念相关              |
| **BM25/关键词** | TF-IDF 变种    | 精确匹配、专有名词、ID          |
| **图检索**      | 实体关系遍历       | 多跳关联（"A 的同事 B 负责的项目"） |
| **结构化过滤**    | SQL WHERE 条件 | 按时间/用户/标签预过滤          |

## Rerandker

召回100个候选，Reranker选出最相关的Top-5注入Prompt

| 模型                     | 类型            | 特点             |
| ---------------------- | ------------- | -------------- |
| **bge-reranker-large** | Cross-encoder | 开源，中文好，延迟中等    |
| **Cohere Rerank**      | API           | 精度高，按调用付费      |
| **GPT-4/Claude**       | LLM-as-Judge  | 精度最高，最贵，适合关键场景 |

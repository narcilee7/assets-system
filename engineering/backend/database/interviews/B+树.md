# B+ 树深度 Review（面试版）

## 一、B+ 树是什么

B+ 树是一种**多路平衡查找树**，是 B 树的变种。核心特征：

```
┌─────────────────────────────────────────────────────────┐
│  非叶子节点（Internal Node）                             │
│  • 只存储键值（Key），不存储实际数据                      │
│  • 每个键对应一个指针，指向子节点                         │
│  • 所有键在叶子节点中有一份冗余副本                        │
├─────────────────────────────────────────────────────────┤
│  叶子节点（Leaf Node）                                    │
│  • 存储所有键值 + 实际数据（或数据地址）                   │
│  • 叶子节点之间用**双向链表**连接                         │
│  • 这是 B+ 树支持高效范围查询的根本原因                   │
└─────────────────────────────────────────────────────────┘
```

## 二、为什么 InnoDB 选 B+ 树（面试必考）

### 2.1 与 B 树对比

| 维度 | B 树 | B+ 树 |
|---|---|---|
| **数据存储** | 非叶子节点也存数据 | 只有叶子节点存数据 |
| **节点容量** | 一个节点存更少键（因为数据占空间） | 一个节点存更多键（纯键值） |
| **树高度** | 更高 | 更矮胖 |
| **范围查询** | 需要中序遍历，跨节点回溯 | 叶子链表顺序遍历，一次 I/O 流 |
| **查询稳定性** | 最好 O(log n)，最坏 O(log n) | 所有查询都是 O(log n)，稳定 |

**一句话记忆**：B+ 树把数据"压到"叶子层，非叶子层只当"路标"，所以路标更密集，树更矮，磁盘 I/O 更少。

### 2.2 与红黑树对比

- 红黑树是**二叉树**，高度为 O(log₂n)
- B+ 树是**多叉树**，InnoDB 中一个节点 16KB，通常能存 1000+ 个键
- 假设 1000 万数据：
  - 红黑树高度 ≈ 24 层，最多 24 次磁盘 I/O
  - B+ 树高度 ≈ 3 层，最多 3 次磁盘 I/O
- **磁盘 I/O 是数据库的瓶颈**，B+ 树完胜

### 2.3 与哈希表对比

- 哈希表：O(1) 点查，但**不支持范围查询和排序**
- B+ 树：O(log n) 点查，天然支持范围查询（`BETWEEN`、`>`、`<`、`ORDER BY`）

## 三、InnoDB 中的 B+ 树实现细节

### 3.1 页（Page）是 B+ 树的节点

```
┌────────────────────────────────────────┐
│  InnoDB 最小存储单元：Page = 16KB      │
│  一个 Page 就是一个 B+ 树节点          │
└────────────────────────────────────────┘
```

**页的结构**：

```
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│ File     │ Page     │ Infimum  │ User     │ Free     │ Page    │ Directory │ File
│ Header   │ Header   │ +        │ Records  │ Space    │ Trailer │ (Slot)    │ Trailer
│ (38B)    │ (56B)    │ Supremum │          │          │         │           │
└──────────┴──────────┴──────────┴──────────┴──────────┘
           ↑                                    ↑
        记录按照主键顺序排列              用于二分查找的稀疏索引
```

### 3.2 聚簇索引（Clustered Index）的 B+ 树

```
                    ┌─────────────┐
                    │  根节点      │
                    │  [10|30|50] │
                    └──────┬──────┘
           ┌─────────────┼─────────────┐
           ↓             ↓             ↓
    ┌────────────┐ ┌────────────┐ ┌────────────┐
    │ [5|8|10]   │ │ [20|25|30] │ │ [40|45|50] │
    │ 指针指向    │ │ 指针指向    │ │ 指针指向    │
    │ 叶子节点    │ │ 叶子节点    │ │ 叶子节点    │
    └──────┬─────┘ └──────┬─────┘ └──────┬─────┘
           └─────────────┬─────────────┘
                         ↓
    ┌────────────────────────────────────────────────────┐
    │  叶子节点（双向链表）                                │
    │  ┌─────┐   ┌─────┐   ┌─────┐   ┌─────┐   ┌─────┐  │
    │  │ 1,  │ → │ 5,  │ → │ 8,  │ → │ 10, │ → │ 20, │  │
    │  │ 行数据│   │ 行数据│   │ 行数据│   │ 行数据│   │ 行数据│  │
    │  └─────┘ ← └─────┘ ← └─────┘ ← └─────┘ ← └─────┘  │
    └────────────────────────────────────────────────────┘
```

**关键细节**：
- 叶子节点存储的是**完整的行数据**（聚簇索引）
- 非叶子节点存储的是**主键值 + 子节点指针**
- 叶子节点按主键顺序排列，并通过前后指针连接

### 3.3 二级索引（Secondary Index）的 B+ 树

```
二级索引叶子节点不存完整数据，只存：
┌────────────────────────────────────────┐
│  [索引列值]  +  [主键值]                │
│  例如：idx_name 叶子节点存储             │
│  ["Alice", 100], ["Bob", 200]...       │
│                                        │
│  需要回表时：拿主键值去聚簇索引查完整数据  │
└────────────────────────────────────────┘
```

## 四、容量估算（面试高频计算题）

### 4.1 假设条件

- 页大小：16KB
- 主键类型：BIGINT（8 字节）
- 指针大小：6 字节（InnoDB 的 Page Pointer）
- 每行数据平均大小：1KB

### 4.2 计算过程

**非叶子节点**：
- 每个键值对占用：8B（主键）+ 6B（指针）= 14B
- 一个非叶子页能存：16KB / 14B ≈ **1170 个键值对**

**叶子节点**：
- 每行数据 1KB
- 一个叶子页能存：16KB / 1KB = **16 条记录**

**树高度与总容量**：

| 高度 | 非叶子节点 | 叶子节点记录数 | 总记录数 |
|---|---|---|---|
| 1 | 根节点（1 页） | 直接存数据 | 16 |
| 2 | 根 → 1170 个叶子 | 1170 × 16 | ≈ 1.8 万 |
| 3 | 1170 × 1170 个叶子 | 1170² × 16 | ≈ **2100 万** |
| 4 | 1170³ 个叶子 | 1170³ × 16 | ≈ **250 亿** |

**面试金句**："InnoDB 中，通常 3 层 B+ 树就能存下 2000 万行数据，查询只需要 3 次磁盘 I/O。"

## 五、页分裂（Page Split）与页合并

### 5.1 页分裂

```
场景：向已满的叶子页插入新记录

原叶子页（已满）：
┌─────┬─────┬─────┬─────┬─────┬─────┐
│ 10  │ 20  │ 30  │ 40  │ 50  │ 60  │
└─────┴─────┴─────┴─────┴─────┴─────┘

插入 25：
1. 申请一个新页
2. 将原页数据分裂：一部分留在原页，一部分移到新页
3. 更新父节点的指针

分裂后：
原页：┌─────┬─────┬─────┐  新页：┌─────┬─────┬─────┐
      │ 10  │ 20  │ 25  │       │ 30  │ 40  │ 50  │ 60（可能继续分裂）
      └─────┴─────┴─────┘       └─────┴─────┴─────┘
```

**页分裂的影响**：
- 需要申请新页（磁盘 I/O）
- 需要更新父节点指针
- 数据不再严格顺序存储，产生碎片
- **自增主键**顺序插入时，永远在页尾追加，几乎不触发页分裂

### 5.2 页合并

删除数据导致页利用率低于 50% 时，InnoDB 会尝试与相邻页合并。

## 六、查询过程拆解

### 6.1 等值查询 `WHERE id = 30`

```
1. 从缓冲池（Buffer Pool）读取根节点页
2. 在根节点页内二分查找，确定 30 在 [10, 30) 还是 [30, 50) 区间
3. 根据指针读取对应的非叶子页（或叶子页）
4. 重复二分查找，直到到达叶子页
5. 在叶子页内二分查找，定位到 id=30 的行数据
```

**耗时**：3 次页读取（假设树高 3），页内二分查找是内存操作，极快。

### 6.2 范围查询 `WHERE id BETWEEN 20 AND 50`

```
1. 先按等值查询找到 id=20 的叶子节点
2. 顺着叶子节点的**双向链表**向后遍历
3. 直到遇到 id>50 的记录停止
```

**优势**：不需要回溯父节点，链表遍历是顺序 I/O，效率极高。

## 七、几个容易混淆的点

| 问题 | 答案 |
|---|---|
| B+ 树的非叶子节点存数据吗？ | **不存**，只存键值和指针 |
| 叶子节点之间是什么结构？ | **双向链表**，支持前后遍历 |
| 为什么主键推荐自增整数？ | 顺序插入，减少页分裂，占用空间小 |
| 二级索引叶子存什么？ | **索引列值 + 主键值**，需要回表 |
| B+ 树是平衡树吗？ | 是，所有叶子节点在同一层 |
| 页内如何查找？ | **二分查找**（Page Directory 辅助） |

---

## 八、一句话总结

> B+ 树通过"数据下沉到叶子、非叶子纯做路标、叶子链表串联"三个设计，在磁盘 I/O 场景下实现了**稳定的 O(log n) 点查**和**高效的范围查询**，这是 InnoDB 选择它的根本原因。

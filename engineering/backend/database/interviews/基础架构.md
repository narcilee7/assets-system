## 1. 画出 MySQL 的逻辑架构图，并说明各层职责

**核心答案：**

MySQL Server 层 + 存储引擎层，两层结构。

```
┌─────────────────────────────────────────┐
│           连接层 (Connectors)            │
│    TCP/IP, Unix Socket, 认证, 线程池     │
├─────────────────────────────────────────┤
│           服务层 (Server Layer)          │
│  ┌─────────┐ ┌─────────┐ ┌──────────┐ │
│  │ 查询缓存 │ │ 分析器  │ │  优化器  │ │
│  │(8.0移除) │ │ 词法/语法│ │ 执行计划 │ │
│  └─────────┘ └─────────┘ └──────────┘ │
│  ┌─────────┐ ┌─────────┐ ┌──────────┐ │
│  │ 执行器  │ │ 内置函数│ │  视图/触发器│ │
│  │调用引擎 │ │ 存储过程│ │  等      │ │
│  └─────────┘ └─────────┘ └──────────┘ │
├─────────────────────────────────────────┤
│         引擎层 (Storage Engines)         │
│    InnoDB / MyISAM / Memory / Archive   │
│    负责：存储、索引、锁、事务、缓存        │
├─────────────────────────────────────────┤
│         存储层 (File System)             │
│    .frm / .ibd / .MYD / .MYI / Redo     │
│    Log / Binlog / Undo Log               │
└─────────────────────────────────────────┘
```

**面试要点：**
- 连接层只做连接和认证，不做 SQL 解析
- 服务层是 MySQL 的核心，跨引擎的通用逻辑都在这里
- 引擎层是插件式的，可以 `SHOW ENGINES` 查看
- 存储层就是裸文件系统

## 2. Server 层和存储引擎层是怎么交互的？

**核心答案：**

通过 **Handler API** 交互。Server 层调用引擎提供的标准接口，引擎层实现这些接口。

关键接口（伪代码）：
```c
// 打开表
handler->ha_open()
// 读取一行
handler->ha_read()
// 写入一行
handler->ha_write()
// 更新一行
handler->ha_update()
// 删除一行
handler->ha_delete()
// 关闭表
handler->ha_close()
```

**面试延伸：**
- 这是**插件式架构**的核心，InnoDB 在 MySQL 5.5 之前是第三方插件，后来被 Oracle 收购后成为默认
- Server 层不 care 数据存在哪里（磁盘/内存/远程），只 care 接口返回了行数据
- 引擎层对 Server 层是黑盒，但 Server 层会传 `hint`（比如"我要用索引 X"）给引擎

## 3. 一条 `SELECT` 语句的完整执行流程

**核心答案（分步）：**

1. **连接器**：TCP 握手 → 认证（用户名/密码/权限）→ 建立连接（分配线程）
2. **查询缓存**（5.7 及以前）：以 SQL 为 key 查缓存，命中直接返回（8.0 已移除）
3. **分析器**：
   - 词法分析：把 `SELECT id FROM user WHERE name='tom'` 拆成 token（`SELECT`、`id`、`FROM`、`user`...）
   - 语法分析：生成解析树（Parse Tree），检查语法是否合法
4. **优化器**：
   - 生成多个执行计划
   - 基于成本（Cost-Based）选择最优：统计索引 Cardinality、估算扫描行数、IO 成本
   - 决定走哪个索引、JOIN 顺序、是否用临时表
5. **执行器**：
   - 调用引擎接口：`handler->ha_open()` → `ha_read()` → ... → `ha_close()`
   - 对返回的每一行做 `WHERE` 条件过滤（没有索引的情况下）
   - 把结果集返回客户端
6. **存储引擎**：按执行计划读 Buffer Pool 或磁盘，返回行数据

**面试陷阱点：**
- 执行器才做 `WHERE` 过滤！如果列没索引，执行器会逐行判断，引擎只是"无脑"把数据读上来
- 有索引时，引擎会利用索引过滤，减少返回给 Server 层的行数

## 4. 查询缓存为什么被移除了？

**核心答案：**

MySQL 5.7 及以前有，8.0 彻底移除。

**原因：**
1. **命中率极低**：任何对表的写操作（INSERT/UPDATE/DELETE/ALTER）都会使该表的所有查询缓存失效。写多读少的场景缓存几乎没用。
2. **锁竞争**：查询缓存是一个全局锁结构，高并发下成为瓶颈。
3. **缓存粒度太粗**：以完整 SQL 字符串为 key，哪怕多一个空格、注释不同，就匹配不上。
4. **有更好替代**：应用层缓存（Redis/Memcached）、Buffer Pool 本身就能缓存热点数据。

**面试加分：**
- 如果你用的是 5.7，可以 `query_cache_type = 0` 关闭
- 8.0 移除后，省下来的代码复杂度用来优化其他模块

## 5. MySQL 的连接是进程还是线程？连接池怎么保持活跃？

**核心答案：**

- **线程**。MySQL 每来一个连接就分配一个线程（`thread_handling` 默认 one-thread-per-connection）。
- MySQL 企业版有线程池（Thread Pool），社区版需要插件或自己实现。

**连接池保持活跃：**
- 应用层连接池（HikariCP、Druid）会维护连接，定期发 `SELECT 1` 心跳检测
- MySQL 服务端有 `wait_timeout`（非交互式连接超时，默认 8 小时）和 `interactive_timeout`（交互式）
- 连接长时间不活跃会被服务端断开，下次用就报 `Communications link failure`

**面试延伸：**
- `max_connections` 默认 151，打满后新连接报错
- `Too many connections` 时，连 `root` 都连不上（除非配置了 `max_connections + 1` 给 root 预留）

## 6. 分析器阶段语法错误，报错从哪层抛出？

**核心答案：**

从 **分析器（Parser）** 抛出，属于 Server 层。

比如：
```sql
SELECT * FORM user;  -- 注意 FORM 不是 FROM
```
报错：`ERROR 1064 (42000): You have an error in your SQL syntax...`

**注意：**
- 词法分析阶段（Lexer）不会报错，它只是拆分 token
- 语法分析阶段（Parser）根据语法规则检查，发现 `FORM` 不是合法关键字，抛出错误
- 如果语法正确但表不存在（`SELECT * FROM not_exist_table`），这是**语义错误**，在执行器或引擎层才报（`Unknown table`）

## 7. 优化器选择索引的依据是什么？

**核心答案：**

**基于成本（Cost-Based Optimizer, CBO）**，不是基于规则（RBO）。

成本估算因素：
1. **IO 成本**：读取索引页和数据页的磁盘 IO 次数
2. **CPU 成本**：比较、排序、过滤的 CPU 消耗
3. **索引统计信息**：`SHOW INDEX FROM table` 中的 `Cardinality`（估算值，不是精确值）
4. **扫描行数估算**：`EXPLAIN` 里的 `rows` 就是优化器估算的

**优化器可能选错索引：**
- 统计信息不准确（`ANALYZE TABLE` 可更新）
- 索引选择性差（比如性别列）
- 数据分布不均匀（某个值占 90%）

**面试加分：**
- 可以用 `FORCE INDEX` 强制走某个索引，但生产环境不推荐
- `optimizer_switch` 可以控制优化器行为（比如是否启用 ICP、MRR 等）

## 8. `optimizer_trace` 是什么？怎么用？

**核心答案：**

`optimizer_trace` 是 MySQL 5.6+ 提供的**优化器追踪工具**，可以看到优化器生成执行计划的完整决策过程。

**用法：**
```sql
-- 开启
SET optimizer_trace="enabled=on";
-- 执行你的 SQL
SELECT * FROM user WHERE a=1 AND b=2;
-- 查看追踪结果
SELECT * FROM information_schema.OPTIMIZER_TRACE;
```

**能看到什么：**
- 优化器考虑了哪些索引
- 每个索引的估算成本（IO 成本、CPU 成本）
- 为什么最终选了某个索引
- JOIN 顺序的尝试过程

**面试场景：**
- 线上 SQL 突然不走索引了，用 `optimizer_trace` 看是不是统计信息过期
- 排查 `filesort` 和 `temporary` 是怎么产生的

## 9. 执行器调用引擎时，`rows_examined` 和 `rows_sent` 分别代表什么？

**核心答案：**

- **`rows_examined`**：引擎返回给 Server 层的总行数（Server 层检查过的行数）
- **`rows_sent`**：最终返回给客户端的行数

**关键理解：**
- 如果 `WHERE` 条件没有索引，`rows_examined` 可能远大于 `rows_sent`
  - 例：表有 100 万行，没有索引，执行器要逐行检查 100 万次，最后只返回 1 行
  - `rows_examined = 1000000`, `rows_sent = 1`
- 如果有索引且能过滤，`rows_examined` 会接近 `rows_sent`

**面试陷阱：**
- `rows_examined` 不是磁盘读取次数！是 Server 层处理的行数
- 真正的磁盘 IO 要看 `Handler_read_*` 状态变量

## 10. 预处理语句（Prepared Statement）在架构哪一层处理？优势？

**核心答案：**

在 **Server 层** 处理。

**流程：**
1. `PREPARE stmt FROM 'SELECT * FROM user WHERE id = ?'`
2. 分析器解析 SQL 模板，生成解析树，缓存起来
3. `SET @a = 1`
4. `EXECUTE stmt USING @a` → 执行器直接拿缓存的解析树，填入参数执行

**优势：**
1. **防 SQL 注入**：参数是值，不是 SQL 字符串的一部分
2. **减少解析开销**：复杂 SQL 只需解析一次，多次执行复用
3. **减少网络传输**：后续只需传参数，不用传完整 SQL

**面试延伸：**
- JDBC 的 `PreparedStatement` 底层就是用的 MySQL 协议中的 COM_STMT_PREPARE / COM_STMT_EXECUTE
- 注意：预处理语句也有缓存上限，`max_prepared_stmt_count` 默认 16382

## 11. MySQL 通信协议是什么？长连接和短连接？

**核心答案：**

MySQL 客户端-服务端通信基于 **TCP/IP** 或 **Unix Socket**，协议是 **MySQL Protocol**（应用层协议）。

**长连接 vs 短连接：**
- **短连接**：每次 SQL 执行完就断开。连接开销大（TCP 握手 + 认证），适合低频访问。
- **长连接**：连接建立后保持，多次 SQL 复用。减少连接开销，但占用服务端线程和内存。

**长连接的问题：**
- 内存碎片：MySQL 执行过程中申请的内存（比如 `sort_buffer`）不会完全释放，连接越久内存占用越大
- 解决：**定期断开重连**（连接池设置 `maxLifetime`），或执行 `mysql_reset_connection`（5.7+，重置连接状态不清空会话变量）

**面试加分：**
- MySQL 协议是半双工的：一个连接同一时间只能发或收，不能同时双向
- 大数据量查询时，服务端发数据，客户端必须读完才能发下一条命令

## 12. 连接数被打满了，新连接会怎样？`back_log` 是干嘛的？

**核心答案：**

- **`max_connections`** 默认 151，满了之后新连接报错：`ERROR 1040: Too many connections`
- 即使你是 root，也连不上（除非配置了 `max_connections + 1` 给 root 预留）

**`back_log`：**
- TCP 监听队列的大小。当 MySQL 主线程来不及 accept 新连接时，新连接先挂在 `back_log` 队列里
- 默认 50（5.7）或自动计算（8.0），可以调大
- 如果 `back_log` 也满了，客户端会收到 `ECONNREFUSED`

**面试排查：**
```sql
SHOW STATUS LIKE 'Threads_connected';  -- 当前连接数
SHOW STATUS LIKE 'Threads_running';     -- 正在执行 SQL 的线程数
SHOW PROCESSLIST;                      -- 看每个连接在干嘛
```

**如果已经满了怎么救？**
- 如果能连上：`KILL <id>` 杀掉空闲连接
- 如果连不上：只能从 OS 层 `kill -9` 掉 MySQL 进程重启（最后手段）

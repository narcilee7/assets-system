接收方：

告诉：

例如：

```text

```

---

第二：

简称：

```text

```

不是：

而是：

自己：

表示：

> 我认为网络还能承受多少。

整整：

---

真正：


如果接收方只有 16KB 空间，而网络还能承受 1MB，那么只能发 16KB；如果接收方能收 1MB，但网络拥塞，只允许发 32KB，那么也只能发 32KB。

# 为什么 ACK 能提高吞吐量？

现在：

终于：

回到：

第一题。

Stop-and-Wait：

```text
发1KB

↓

等100ms
```

Sliding Window：

```text
连续发64KB

↓

等ACK
```

虽然：

RTT：

一样。

但是：

一次：

发送：

的数据：

变多。

所以：

带宽：

真正：

利用起来。

这里有一个经典公式，面试中经常出现：

> **理论吞吐量 ≈ Window Size / RTT**

例如：

窗口：

64KB。

RTT：

100ms。

那么：

```text
64KB / 0.1s ≈ 640KB/s
```

如果窗口扩大到 1MB，而 RTT 不变，理论吞吐量也会近似扩大到原来的 16 倍。这就是为什么**高带宽、高时延（高 BDP，Bandwidth-Delay Product）网络必须使用大窗口**，也是后来 TCP Window Scaling 选项出现的原因。

# 到这里，TCP 已经变成一个完整系统

我们已经有了：

* **Sequence Number**：标识字节位置。
* **ACK**：同步连续接收边界。
* **Sliding Window**：允许发送方持续发送而不是停等。

但还有两个关键问题没有解决：

1. **如果接收方 Buffer 满了怎么办？**——这就是 **Flow Control（流量控制）**。
2. **如果网络本身拥塞了怎么办？**——这就是 **Congestion Control（拥塞控制）**。

这两个问题名字很像，但解决的是完全不同的问题：

* **Flow Control** 解决的是**终点处理不过来**（Receiver Too Slow）。
* **Congestion Control** 解决的是**网络承载不过来**（Network Too Busy）。

很多面试都会先问一句：

> **Flow Control 和 Congestion Control 有什么区别？**

如果没有真正理解滑动窗口，这两个概念几乎一定会混淆。

因此，我建议下一章先学习 **Flow Control（流量控制）**，把接收窗口（`rwnd`）彻底弄清楚，再进入拥塞控制。这样整个 TCP 的知识体系会保持一致且层层递进。

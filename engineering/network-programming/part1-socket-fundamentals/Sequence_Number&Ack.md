# Chapter 6 Sequence Number & ACK

这一章只有一句话。

> **TCP 到底在传什么？**

很多人会回答：

> TCP 传 Packet。

错。

TCP 从来不知道 Packet。

TCP 的世界里只有：

> **连续不断的 Byte Stream（字节流）。**

这是理解 TCP 的第一原则。

---

# TCP 的世界里没有消息

假设：

```python
sock.send(b"Hello")
sock.send(b"World")
```

应用程序认为：

```
Message1

Hello
```

```
Message2

World
```

TCP 看见的是：

```
HelloWorld
```

只有：

```
48
65
6c
6c
6f
57
6f
72
6c
64
```

十个连续字节。

TCP 根本不知道：

哪里是 Hello。

哪里是 World。

因此：

Sequence Number 永远描述：

**字节的位置。**

不是：

消息的位置。

---

# TCP 可以理解成一本书

这是我最喜欢的理解方式。

假设一本书：

```
Page 1

Page 2

Page 3

...

Page 1000
```

TCP 并不是：

```
第几个包
```

而是：

```
第几个字节。
```

例如：

```
Seq = 5000
Length = 1000
```

意思：

```
5000

↓

5999
```

这一包负责：

这 1000 个字节。

---

# 为什么不是 Packet Number？

这是 TCP 最重要的设计思想之一。

假设：

第一包：

```
100 Byte
```

第二包：

```
1400 Byte
```

第三包：

```
600 Byte
```

如果：

编号：

```
Packet1

Packet2

Packet3
```

第二包丢了。

服务器只能知道：

> 第二包没到。

但是：

到底：

少了多少数据？

不知道。

如果：

按 Byte。

```
0~99

100~1499

1500~2099
```

第二包丢失。

立刻知道：

```
100~1499
```

缺失。

所以：

TCP 可以：

精准重传。

---

# Sequence Number 的本质

很多人背：

```
Sequence Number

序列号
```

我觉得这个翻译不好。

我更喜欢：

> **Byte Offset（字节偏移）**

例如：

```
Seq = 5000
```

真正意思：

> **这一段数据，从第 5000 个字节开始。**

不是：

第 5000 个包。

---

# ACK 真正在确认什么？

这是整个 TCP 最容易误解的地方。

假设：

客户端发送：

```
Seq = 1000

Length = 500
```

服务器收到。

ACK：

不是：

```
ACK = 1000
```

而是：

```
ACK = 1500
```

什么意思？

> **1000~1499 全部收到，请从 1500 开始继续发。**

注意。

ACK：

永远表示：

> **Next Expected Byte**

不是：

Last Received Byte。

这个区别非常重要。

---

# 为什么这样设计？

假设：

收到：

```
1000~1499
```

ACK：

```
1500
```

后来：

收到：

```
1500~1999
```

ACK：

```
2000
```

ACK 一直表示：

```
下一块。
```

这样：

发送方：

完全知道：

接收方：

已经连续收到哪里。

---

# 为什么叫累计确认（Cumulative ACK）

假设：

客户端：

发送：

```
0~999

1000~1999

2000~2999
```

服务器：

全部收到。

ACK：

只需要：

```
3000
```

一句话：

表示：

```
0~2999
```

全部确认。

不用：

三个 ACK。

这就是：

累计确认。

---

# 乱序怎么办？

真正开始有意思。

例如：

网络：

发生：

```
1000~1499

↓

丢了
```

但是：

```
1500~1999
```

先到了。

服务器：

怎么办？

很多新人会说：

ACK：

2000。

不是。

TCP：

回复：

```
ACK = 1000
```

为什么？

因为：

TCP：

要求：

**按连续字节确认。**

虽然：

1500~1999

已经收到了。

但是：

1000~1499

没有。

所以：

应用层：

还不能得到：

连续的数据流。

于是：

ACK：

仍然：

1000。

---

# 接收缓冲区到底在干什么？

这就是 Receive Buffer。

例如：

```
已经收到：

1500~1999
```

但是：

ACK：

还是：

1000。

这些数据：

不会丢。

而是：

放在：

```
Receive Buffer

↓

Out-of-order Queue
```

等待：

```
1000~1499
```

到来。

一旦：

缺口：

补齐。

ACK：

直接：

跳：

```
2000
```

不是：

1500。

不是：

1999。

而是：

2000。

因为：

连续了。

---

# 为什么 ACK 会突然跳？

例如：

服务器：

已经缓存：

```
1500~1999

2000~2499

2500~2999
```

一直：

ACK：

```
1000
```

终于：

```
1000~1499
```

来了。

ACK：

不是：

```
1500
```

而是：

```
3000
```

因为：

整个：

```
1000~2999
```

全部连续了。

所以：

ACK：

直接：

跳过去。

这是累计确认的威力。

---

# 为什么 Duplicate ACK 会出现？

假设：

一直：

缺：

```
1000~1499
```

后面：

不断收到：

```
1500~1999

2000~2499

2500~2999
```

服务器：

会不断回复：

```
ACK=1000

ACK=1000

ACK=1000
```

这些：

就是：

Duplicate ACK。

发送方看到连续多个相同的 ACK（经典 TCP 中通常是 **3 个重复 ACK**），会推断：

> **不是整个网络断了，而是中间某一段数据很可能丢了。**

于是：

立即重传。

这就是：

Fast Retransmit（快速重传）。

注意，它不是因为“收到三个 ACK”，而是因为**收到三个重复的 ACK**。

---

# 整个 TCP 可以重新理解了

到目前为止，TCP 的核心其实可以浓缩成一句话：

> **发送方不断发送带有字节区间的数据；接收方不断告诉发送方："我已经连续收到哪里了，请从这里继续。"**

你可以把它看成一个连续的数据流同步协议，而不是一个"发包-收包"协议。

发送方维护自己的发送窗口和未确认数据；接收方维护自己的接收缓冲区和连续接收边界；ACK 就是双方同步这个边界的机制。

# 朴素队列

这是一个非常值得讲的点。**Naive Queue（朴素队列）**其实不是算法问题，而是 **Go Slice 的内存模型**问题。

很多 Go 初学者都会写出这样的 Queue：

```go
type Queue[T any] []T

func (q *Queue[T]) Enqueue(v T) {
	*q = append(*q, v)
}

func (q *Queue[T]) Dequeue() (T, bool) {
	var zero T
	if len(*q) == 0 {
		return zero, false
	}

	v := (*q)[0]
	*q = (*q)[1:]
	return v, true
}
```

乍一看：

* Enqueue：`append()` → 均摊 O(1)
* Dequeue：`q = q[1:]` → O(1)

看起来完美。

实际上，它隐藏了一个 Go 中非常经典的坑。

---

# 第一步：理解 Slice

首先要记住：

> **Slice 不是数组。**

Slice 本质上只是一个 Header。

```go
type SliceHeader struct {
	Data uintptr
	Len  int
	Cap  int
}
```

例如：

```go
q := []int{1,2,3,4,5}
```

内存：

```
Slice Header

+------+-----+-----+
| ptr  | len | cap |
+------+-----+-----+
    │
    ▼

Array

+---+---+---+---+---+
| 1 | 2 | 3 | 4 | 5 |
+---+---+---+---+---+
```

真正的数据：

```
在 Array

不是 Slice
```

---

# 第二步：Dequeue 发生了什么？

执行：

```go
q = q[1:]
```

很多人脑子里的画面：

```
删除了：

1
```

其实：

**没有任何元素被删除。**

真正发生的是：

```
原来：

ptr ---> 1

len = 5

cap = 5
```

变成：

```
ptr ---> 2

len = 4

cap = 4
```

数组：

```
+---+---+---+---+---+
| 1 | 2 | 3 | 4 | 5 |
+---+---+---+---+---+
```

完全没有变化。

只是：

```
Slice Header

指向第二个元素。
```

---

# 第三步：为什么这是 O(1)

因为：

修改的只有：

```
ptr

len

cap
```

三个字段。

根本没有：

```
copy()

memmove()
```

所以：

```
O(1)
```

---

# 第四步：真正的问题

来看一个例子。

```go
q := make([]int, 0)

for i := 0; i < 1_000_000; i++ {
	q = append(q, i)
}
```

底层：

```
cap

≈1000000
```

现在：

```go
for i := 0; i < 999999; i++ {
	q = q[1:]
}
```

按理说：

队列里面：

```
只剩：

1 个元素
```

很多人觉得：

```
应该只占：

8 Byte
```

实际上：

底层：

```
还是：

1000000 个元素的数组
```

为什么？

因为：

最后那个元素：

```
仍然引用：

整个数组
```

GC 不敢释放。

---

# 内存长什么样？

开始：

```
Slice

↓

+-------------------------------------------+
|1|2|3|4|5|6|...|999999|
+-------------------------------------------+
```

连续：

```
Dequeue
```

以后：

```
Slice

↓

                 +--------------------------+
                 |999999|
                 +--------------------------+
```

但是：

底层：

```
整个数组

仍然存在。
```

因为：

```
ptr

落在里面。
```

---

# GC 为什么不能回收？

Go GC：

只知道：

```
还有 Slice

↓

指向这里
```

不知道：

```
前面那些元素

以后

还会不会访问。
```

因此：

整个数组：

```
Live
```

---

# 更严重的问题（对象引用）

假设：

```go
type User struct {
	Name string
	Data [1024 * 1024]byte
}
```

Queue：

```go
[]*User
```

里面：

```
100000 个 User
```

你：

```
Dequeue

99999 次
```

队列：

只剩：

```
一个 User
```

但是：

底层数组：

```
仍然保存：

99999 个指针。
```

即使这些元素已经不在 `len` 范围内，**底层数组中的指针值仍然存在**。只要这个底层数组还活着，这些对象就仍然可能被 GC 认为是可达的，因此无法及时回收。

所以：

**内存泄漏的不是 Slice，而是底层数组持有的引用。**

---

# 那 Stack 为什么没有这个问题？

Stack：

```go
s = s[:n]
```

缩短的是：

```
尾部
```

而且：

通常都会：

```go
var zero T
s[n] = zero
```

这样：

```
最后一个元素

置空。
```

GC：

可以释放。

同时：

随着不断 Pop，

容量没有因为移动头部而浪费。

---

# 工程上怎么解决？

方案一：

当：

```text
head > cap/2
```

重新整理：

```go
newBuf := make([]T, len(q))
copy(newBuf, q)
q = newBuf
```

把真正的数据：

复制到：

```
新的数组。
```

---

方案二：

维护：

```go
type Queue[T any] struct {
	buf  []T
	head int
}
```

Dequeue：

```go
q.head++
```

而不是：

```go
q = q[1:]
```

当：

```
head

太大
```

统一：

```
copy()
```

一次。

很多工程：

这么做。

---

方案三（最佳）

直接：

```
Ring Buffer
```

也就是：

循环数组。

Go、Kafka、Disruptor、高性能消息队列基本都是这种实现。

---

## 为什么还要学 Naive Queue？

因为它是理解 Ring Buffer 的前置知识。

Ring Buffer 解决的不是算法复杂度问题，而是：

1. 避免 Slice 不断向前切片导致的大数组长期存活。
2. 避免频繁的数据搬移（`copy`）。
3. 保持 FIFO 操作始终为 O(1)。

所以 Naive Queue 并不是"错误实现"，它在数据量较小、生命周期较短的场景完全可以使用；真正的问题是在**长生命周期、高吞吐量的队列**中，它会造成内存利用率越来越差。这正是 Ring Buffer 存在的原因，也是 Go 后端开发中更推荐的队列实现。
